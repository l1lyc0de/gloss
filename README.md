# Gloss

**点一下单词，释义直接出来。**

不用先按住选中，不用等菜单弹出来，不用再点一次「翻译」——
手指落下的那一下，中文释义就在下面了。给英文加词典的工具不少，
绝大多数是「选中 → 等菜单 → 点翻译」三步；这里是一步。
一屏三十个生词的时候，这个差别就是「读得下去」和「读不下去」。

快是有代价换来的，代价在 `dict.js` 里：32 万词的词典按首两字母切成 647 个分片，
进一节之前先把这一节要用的几片准备好（`ensureSectionDict`），所以点下去是纯内存查表，
不等网络、不等磁盘。这也是为什么它能全程离线 —— 词典整本在你机器上。

在这个前提下，它是一个**自己带文档的离线阅读器**：导入你手上的
EPUB / PDF / Word / 网页 / 纯文本，全程不联网、不上传。
不只是书 —— 挡在人前面的从来不只有原版书，英文合同、说明书、论文、网页文章，
一样是一屏生词。

> 这句话页面上是可以当场验证的：打开 `/download`，那儿摆着一句英文，点一下试试。
> 演示用的六条词条硬编码在 `public/js/demo.js` 里（从 `public/dict/` 原样抄的），
> 免得为了演示先下 1.6 MB 分片 —— 那正好会把要证明的事情证伪。

这是 [`../Gloss-产品构想.md`](../Gloss-产品构想.md) 的本地实现，对应路线图的**第 1 步**
（管线翻成 JS，做成网页版支持任意导入）。既可以只在本机跑，也可以自己找台机器部署——
`deploy/gloss.service` 就是给后者用的 systemd 模板（见「自建部署」）。

---

## 跑起来

```bash
node gloss/server.js            # → http://localhost:5173
```

零依赖，不用 `npm install`。想在手机上试（同一 Wi-Fi）：

```bash
HOST=0.0.0.0 node gloss/server.js   # 启动时会打印手机能访问的地址
```

词典分片已经生成好了（`public/dict/`，647 个文件，28.8 MB）。如果要重新生成：

```bash
python3 gloss/build/build_dict.py       # 从 ../data/stardict.db 读，约 8 秒
```

## 自建部署

想让它在自己的机器上一直跑着（手机随时能开，不用家里那台电脑开机），
`deploy/gloss.service` 是现成的 systemd 模板。链路是这样的：

```
Cloudflare Tunnel  →  127.0.0.1:5173  →  systemd 跑的 server.js
```

**用隧道而不是 nginx + 证书**，是因为 unit 里写死了 `HOST=127.0.0.1`：
服务只绑本地回环，公网直连不到，也就不用开防火墙端口、不用管证书续期。
代价是多一个 cloudflared 进程。要换成反代也行，把 `HOST` 改回 `0.0.0.0` 之外的做法自己权衡。

```bash
sudo useradd -r -s /usr/sbin/nologin gloss
sudo mkdir -p /opt/gloss/app          # 代码放这里，unit 里的路径写死了
sudo cp deploy/gloss.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now gloss
curl localhost:5173/api/health        # → {"ok":true,...}
```

几个部署时才会踩到的点：

- **`server.js` 认 `cf-connecting-ip`**。限流是按 IP 算的（每分钟 120 次），
  隧道/反代后面所有请求的 `socket.remoteAddress` 都是同一个回环地址 ——
  不认这个头的话，第二个用户就会被第一个用户的额度限流掉。
- **unit 里 `ProtectSystem=strict`，只有 `sync-data/` 可写**。这是故意的：
  服务除了同步码那几 KB 的 JSON，不该往磁盘上写任何东西。
- **`sync-data/` 和 `download/` 都不在 git 里**（见 `.gitignore`）。
  所以拉一份新代码上去，同步数据是空的、APK 下载入口不会出现 ——
  这两个目录得单独传，且**更新代码时务必排除 `sync-data/`**，那是线上用户的真实进度。
- **`android/` 和 `ios/` 都不要传上去**。安卓那边签名密钥在里面；
  iOS 那边没有密钥（证书在钥匙串里），但 `ios/build/` 会攒下 .xcarchive 和 .ipa，
  几十 MB 的东西对生产机毫无用处。

## 安卓 APK

手机上想读，不该要求家里那台电脑开着。`android/` 里是一个**手写的 WebView 壳**，
把 `public/` 整个打进安装包 —— 装完之后这个 App 和任何服务器都没关系了。

```bash
cd gloss/android
./gradlew assembleRelease     # → app/build/outputs/apk/release/app-release.apk
adb install -r app/build/outputs/apk/release/app-release.apk
```

或者一步到位，顺便挂到网页版上给人下：

```bash
./android/publish.sh          # 构建 + 拷到 download/ + 写版本信息
```

需要 JDK 17 和 Android SDK（platform 34 + build-tools 34.0.0），
SDK 路径写在 `android/local.properties`。

**没有引入 Capacitor / Cordova**。那套东西会把一整个 npm 工具链拖进来，
而这个项目从头到尾零依赖，为了套个壳破例不划算。壳统共一个文件、两百行：

- `WebViewAssetLoader` 把 assets 映射成 `https://appassets.androidplatform.net/`。
  不能用 `file:///android_asset/`：网页版是 ES module，file:// 的来源是 `null`，
  模块脚本会被 CORS 直接拦掉，localStorage / IndexedDB 在那底下也不可靠。
- **MIME 自己报**，对着 `server.js` 里那张表抄的。`.mjs`（pdf.js 那两个文件）
  猜不出来会退成 `text/plain`，而模块脚本 MIME 不对浏览器是拒绝执行的 ——
  漏了这一条，PDF 导入会整个哑掉。
- `onShowFileChooser`：WebView 对 `<input type="file">` 默认毫无反应，得自己接。
  取消时也必须回话，漏一次那个 input 就永远卡住，之后再也导不进文档。
- 选择器一律 `*/*`：`accept` 列表里混着 `.epub` 这类扩展名，
  转成 MIME 之后系统选择器反而会把 EPUB 藏起来。格式由 `kindOf()` 按文件名判。
- 返回键：页面没用 history，`goBack()` 是空的，语义在 `app.js` 的 `__glossBack` 里定义
  —— 先关浮层，再退回首页，都没有才收到后台。

`assets.srcDirs` 直接指向 `../../public`，仓库里不留第二份 30 MB 的词典；
改一行网页代码，重新打包就带上了。

### 从网页版下载 APK

`android/publish.sh` 会把包放到 `download/gloss.apk`，server.js 认这个目录：

- `GET /api/apk` → `{available, version, bytes, builtAt, sha256}`，没放包就是 `{available:false}`
- `GET /download/gloss.apk` → 带 `Content-Disposition` 的安装包

前端据此决定露不露入口 —— **服务器上没有包时，入口整个不出现**，
不留一个点下去 404 的链接。露出来的地方分两处：

- **首页**：只对安卓浏览器，在导入入口下面一条轻量横幅。
  iPhone 和电脑上摆一个装不了的按钮是纯噪音。
- **进度页**：所有平台都有（电脑上的人也得知道有这么个东西），
  非安卓设备的提示语会说清「这是安卓包」。

APK 自己内部当然不显示这个入口（`NATIVE` 判断）—— 自己下自己没有意义。

> **`download/` 不能挪进 `public/`。** `public/` 会被整个打进 APK 的 assets，
> 安装包放进去就是让它再装一份自己，体积当场翻倍。
> `sw.js` 也跳过 `/download/`：11 MB 的一次性文件塞进缓存，
> 只会吃掉配额，而且换了新包还会拿到旧的。

### 翻页和目录不能只在正文末尾

原来想翻到下一节，得先把当前这节滚到底 —— 而「我不想读这节了」恰恰是最需要
马上能走的时候。这是本末倒置。

改成滚动时浮出来一条，停手 1.6 秒后自己淡走。**不做常驻**：这个 App 的正文是
拿来连读几十分钟的，屏幕上不能有东西一直杵着。

真正花心思的是「什么时候**不该**出现」—— 一个浮在正文上的东西，时机错了比没有
还烦。四条：

- **正文末尾那一排已经在视野里时不出现。** 同一个功能同时出现两次，
  人会以为那是两个不同的东西。
- **查词卡片开着时不出现**，开卡片的瞬间就收掉。那会儿人在看释义，不是在找路，
  而且两个都停在屏幕下方，会打架。
- **进入一节时先亮一下再淡走。** 不这么做，从不滚动就翻页的人永远发现不了
  有这个东西。
- **提示条要让位。** 浮层占 76–118px，提示条原本在 84–119px，必然重叠。
  浮层出现时给 `body` 加 `.fnav-on`，CSS 把提示条顶到 134px。
  用 class 而不是 `:has()` —— minSdk 26 的机器上 WebView 版本无法预期。

滚动监听**只挂一次**，不在 `renderRead` 里挂：那样读十节就叠十个监听器。

反向断言都在 `test/readnav.js`，十条里有五条是「不该出现」。

### 入口不能只挂在 UA 判断上

有人反馈：安卓 Chrome 上看不到下载入口，换自带浏览器就有。三种安卓 UA
（含 Chrome 的新版精简 UA `Android 10; K`）都复现不出来，最可能是当时服务器上
还没放安装包 —— 那种情况任何浏览器都不该显示入口，是对的。

但这个反馈指出的问题是真的：**入口只有一条路，而那条路挂在 UA 判断上**。
UA 认错、包还没传上去、Service Worker 缓存时机不对，任何一样都会让人得出
「这东西没有手机版」的结论，而且他没有第二个地方可以确认。

所以加了 `/download` —— 一个固定地址的下载页，不依赖 UA、不依赖 SPA、
不依赖 30 MB 词典加载完：一张 Android 卡（版本号、体积、构建日期、SHA-256），
一张 iPhone 卡，一张浏览器卡。`/download` 和 `/download/` 都认，
差一个斜杠就 404 太蠢了；安装包仍在 `/download/gloss.apk`，路由里先接走。

首页的入口也改了：安卓 + 服务器上确实有包 → 照旧直给安装包（一步到位）；
其余平台 → 一条安静的链接指向下载页。原来这里的理由是「iPhone 和电脑上摆一个
装不了的按钮是纯噪音」—— 那对**安装包**成立，对**下载页**不成立。

**iOS 那张卡写的是「添加到主屏幕」，不是「敬请期待」。** Safari 的
Add to Home Screen 现在就能用，装完有图标、整屏、词典缓存在本机，
日常使用和 App 差别不大。原生 iOS 版要走 App Store、要开发者账号，
什么时候做没定 —— 页面上就这么写，不画饼。

顺带修了一个 Service Worker 的洞：`SHELL_FILES` 里**漏了 `js/env.js`**。
`app.js` 直接 import 它，漏掉意味着首次访问就断网的人会白屏（模块解析失败，
整个应用起不来）。运行时缓存能兜住第二次访问，所以一直没暴露。
改这张表时对着 `app.js` 的 import 链数一遍。

### 「检查更新」只是打开一个网址

App 里能看到自己的版本号，旁边一个「检查更新」——点了用**系统浏览器**打开下载页。
就到此为止：不在 App 里检查，不在 App 里下载，不唤起安装器。

这是算过账的。App 内自动更新要两个权限：

- `INTERNET` —— 检查和下载
- `REQUEST_INSTALL_PACKAGES` —— 唤起系统安装器（顺带一提，
  这是投放器类恶意软件的标准形态，侧载时容易被安全软件点名）

而 `AndroidManifest.xml` 里那句注释是这个产品最硬的一张牌：

> 权限表是这句承诺唯一能被外人核实的地方。

任何人 `aapt dump permissions` 一看就知道「我的书传不出去」，不需要相信作者。
加上 `INTERNET` 之后，这个保证从**可核实**降级成**要信你**——
而「不联网、不上传」正是这东西存在的理由。为了省用户两步操作换掉它，换不来。

**而唤起浏览器不需要任何权限**：发一个 `ACTION_VIEW` 的 Intent，抓取动作是浏览器做的。
壳里 `shouldOverrideUrlLoading` 本来就把外链丢给系统浏览器（原本是为了导进来的
网页里的外链），这条路一行新代码都没加。拿到的是自动更新八成的价值，权限表一个字没改。

站点地址**不硬编码在仓库里**——这个仓库是公开的，它属于部署信息。
构建时从 `android/site.properties`（已 gitignore）注入成 `BuildConfig.UPDATE_URL`，
和签名信息走 `keystore.properties` 是同一套办法：**文件不在也能构建**，
那样 `UPDATE_URL` 是空串，「检查更新」入口整个不出现——
和「服务器上没放包时网页版不露下载入口」是同一条规矩，不留点下去没反应的按钮。

版本号通过一个只读的 `@JavascriptInterface` 桥（`NativeBridge`）给到网页，
**只有两个返回编译期常量的方法**，碰不到文件、网络和 Intent。
`addJavascriptInterface` 暴露的是真正的 Java 对象，网页拿到什么就能调什么——
这条界限是刻意划的。

### 三种壳的差别

`js/env.js` 里一个 `NATIVE` 判断管住了绝大部分差异（安卓认域名，iOS 认自定义
scheme）。只有「怎么拿到新版」这一条两个 App 确实不同，那里才看 `PLATFORM`：

| | 网页版 | 安卓 APK | iOS / iPadOS |
|---|---|---|---|
| 词典 | 边查边下，可一次性下全 | **随包安装**，无「下载词典」这回事 | 同左，648 片全在包里 |
| 同步码 | 有，进度备份到 `/api/sync` | **没有**，走「手动备份」 | 同左 |
| Service Worker | 注册 | 不注册（资源本来就在本地） | 同左 |
| 朗读 | 系统 TTS | **没有** —— Android WebView 不实现 Web Speech API | **有**，25 个英文嗓音 |
| 拿新版 | 刷新页面 | 「检查更新」用系统浏览器打开下载页 | App Store 自己提示，App 里不放入口 |

朗读那条在安卓上不是偷懒：WebView 里 `window.speechSynthesis` 根本不存在。
喇叭按钮因此由 CSS 整个藏掉（`.no-tts`），`speak()` 也改成静默返回 ——
复习卡「显示释义」会自动念一次，在那儿每翻一张弹一次「不支持」纯粹是噪音。
真要朗读，得桥接原生 `TextToSpeech`，那是另一件事。
iOS 那栏是白捡的：`util.js` 本来就是特性检测（`'speechSynthesis' in window`），
WKWebView 有，喇叭就自己出来了，一行代码没改。

安装包**不申请 `INTERNET` 权限**。词典在包里、文档由用户自己选、进度只写本机，
权限表是「文档内容不离开这台设备」这句话唯一能被外人核实的地方。

> 签名密钥在 `android/gloss-release.jks`（连同口令一起已 gitignore）。
> **这个文件丢了就发不出更新** —— 换了签名的包 Android 会当成另一个 App，
> 装不上去，只能先卸载，进度和生词本跟着没。请自己备份到仓库以外的地方。

## iOS / iPadOS

`ios/` 里是同样一层薄壳，三个 Swift 文件，和安卓那个 Activity 做的事一一对应。
网页那份 `public/` 两边共用，一个字节都没有分叉。

```bash
open ios/Gloss.xcodeproj              # 或者：
xcodebuild -project ios/Gloss.xcodeproj -scheme Gloss \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build
xcodebuild test -project ios/Gloss.xcodeproj -scheme Gloss \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
./ios/publish.sh                      # archive → .ipa，并核一遍签名和权限
```

需要 Xcode 16 以上（工程用 objectVersion 56，实际在 26.6 上开发）。
`Gloss.xcodeproj/project.pbxproj` 是**手写**的，没有用 XcodeGen 之类的东西 ——
一个只有两个 target 的壳不值得为它引一条工具链。`public/` 是一条 folder reference，
整个目录原样进包，648 个词典分片不用逐个列进工程。

### 为什么是自定义 scheme，不是 `loadFileURL`

和安卓那边不用 `file:///android_asset/` 是同一个坎：网页是 ES module，
`file://` 的来源是 opaque，模块脚本会被 CORS 直接拦掉。

绕过它的办法是开 `allowFileAccessFromFileURLs` —— 那是个私有 preference，
一个要上架的 App 不该把地基压在私有 API 上。所以走 `WKURLSchemeHandler`，
注册 `gloss-app://local/`，这是一个正常的 origin。

注册的 scheme **不能是 http/https**，那是 WebKit 的保留字，注册上去直接抛。
所以 `env.js` 在 iOS 这边认的是 `location.protocol`，不是域名。

自定义 scheme 到底算不算「安全上下文」、`localStorage` 和 `IndexedDB` 认不认它，
是这层壳唯一压了赌注的地方 —— 认不认决定了进度、生词本和整本书的正文存不存得下来。
`ReaderViewController.swift` 末尾那段 `selfCheck` 就是为它写的，只在 Debug 里编进去，
`-GlossSelfCheck 1` 才跑，起来之后自己报一次：

```
origin=gloss-app://local   isSecureContext=true
localStorage=OK            indexedDB=OK
NATIVE=true                dict(按需读分片)=vt. 赔偿, 补偿, 保护, 保障
```

这件事浏览器测不出来（网页版跑在 https 上），安卓也测不出来
（那边是 `WebViewAssetLoader` 给的 https 域名）。只有 WKWebView 说了算。

### 安全区在原生那侧让开

网页的 CSS 只用过 `env(safe-area-inset-bottom)` —— 安卓的 WebView 不延伸到状态栏，
顶部从来不需要留。iOS 上 WKWebView 是铺满整块屏的，直接放上去灵动岛会压在标题上，
阅读页那条 sticky 的 `.rhead` 更是被吃掉一半。

修法不是给 CSS 补一套 `inset-top`（还要照顾 sticky 的粘附位置和横屏时左右的缺口），
而是把 WebView 整个约束进 `safeAreaLayoutGuide`：网页看到的就是一块规规矩矩的矩形，
和安卓那边的处境一字不差，两个平台共用同一份 CSS。让出来的一圈铺同一张纸。

### 选中时不弹系统菜单（和安卓同一条红线）

理由一字不差：这个 App 的卖点就是不用走「选中 → 菜单 → 翻译」那三步，
而系统那个「拷贝 / 查询 / 翻译 / 共享」是原生视图，永远盖在 WebView 上面。
安卓那边要包一层 `ActionMode.Callback`，iOS 这边是 `canPerformAction` 返回 false
再加 `buildMenu` 里把编辑那几组删掉。两边都只清菜单、不碰选择手柄 ——
拖着调整选区那件事必须留着。

`GlossUITests` 盯这一条。**这个测试自己也被验过**：把抑制代码临时拆掉重跑，
它会红，并报出 `menuItems = 5` —— 也就是说长按确实选中了文字、菜单确实有五项、
拦截确实在起作用。一个「什么都没出现」的断言，不这么反着验一次，
和它压根没跑起来是分不清的。

### 不联网这件事，iOS 上怎么说

安卓版把它钉在权限表里：`AndroidManifest.xml` 不申请 `INTERNET`，
任何人用 `aapt2` 都能自己核实。**iOS 没有等价的机制** —— 任何 App 都能联网，
没有一个可核实的声明。这张牌在 iOS 上打不出来，不必假装打得出来。

换成三件能站得住的事：

1. `PrivacyInfo.xcprivacy` 三个数组全空（不追踪、不收集、不用必需理由 API），
   它会进 App Store 的隐私标签
2. 导出的包 entitlements 里只有 team-identifier 和 application-identifier，
   一个要用户授权的能力都没有 —— `ios/publish.sh` 每次发版都打出来给你看
3. 飞行模式下功能一件不少，用户自己就能验

行为上和安卓一模一样：词典全打包、同步码关掉、Service Worker 不注册。

## 它现在能做什么

- **导入 EPUB / PDF / Word(.docx) / 网页(.html) / 纯文本(.txt/.md)**，
  也可以**直接粘贴一段英文**（邮件、报错信息、合同片段这种不值得存成文件的）。
  纯浏览器本地解析，文件一个字节都不上传
- **预览闸门**：先渲染前几段，问一句「这几段读得通吗」，读不通就换一份
- **扫描件直接拒绝**，并说清为什么、建议去找 EPUB 版
- **双栏 PDF 会提示**（检测到版心中缝），但不拦人
- **几乎没有英文的文档会提示**，而不是让人导进来才发现点哪个词都没反应
- **点词即出释义**：音标、中文、考纲标签、常用度 ★。阅读页的释义卡片不遮暗正文，
  可直接点下一个词更新释义；点正文空白处、右上角 × 或按 Escape 关闭，
  文末会留出空间供正文滚动
- **词典页可以直接查任意单词**，不用先导一份文档进来
- **继续阅读**：首页主卡片直接打开最近文档，读前过词作为可选入口；
  空书架突出「导入文档，开始读」，保留点词演示，隐藏零统计
- **阅读设置**：正文右上角 Aa 可即时调整字号、行距和暖纸／深色／跟随系统主题，
  设置自动保存。进度页也有入口，备份、安装和词典管理折叠显示
- **划线 + 写笔记**：按住选中一段就能划线，可以给它写一句自己的话，
  划过的都收在「摘录」里，点一条能跳回原文
- **生词本 + 间隔重复**（1/3/7/14/30/60 天）、连续天数打卡、系统 TTS 朗读
- **免密同步码**：进度和生词本自动备份到本地服务器，换设备输码取回
- 支持页面缩放（含安卓双指缩放）、PWA（可加主屏）、Service Worker 离线

## 几个实现上的决定，和为什么

### 划线不能把单词切成两半

划线是后加的功能，而它插进去的正是这个产品最核心的那条交互所在的位置。
一段划线在 DOM 上是 `<mark>`，正文里每个可查的词是 `<w>` ——
手指拖出来的选区十有八九停在半个单词上，照着原样插标签，
`<mark>` 就会切进 `<w>` 里，一个词被拆成两截，点哪半都查不出东西。
**拿主卖点去换一个附属功能，这笔账怎么算都是亏的。**

所以两端一律吸附到整词（`hl.snap()`，和 Kindle 一个做法），
渲染时按「词 / 边界」两种事件一遍扫过去拼 HTML，
边界永远落在 `<w>` 外面。`test/highlight.js` 里专门有一条盯这个：
划线里的每个 `<w>` 都得是一个完整单词，而且点下去要真的弹出释义卡片。

顺带两条同源的小事：

- 有笔记的划线末尾那个 ✎ 是 CSS `::after` 画的，不是文本。
  查词卡片要拿 `.en` 的纯文本当例句，多一个字符就会混进例句里。
- 已经划过的地方不给再划一条：选区压上去时，工具条给的是「去掉划线」。
  允许叠着划，正文里就会出现深浅不一的层，而且「取消」到底取消哪一条说不清。

跨段选中存成**一条**摘录的多个 `parts`，不是多条。
分成多条的话，删一半留一半，正文里就会留半截线。

### 锚点是「段序号 + 字符偏移」，不是 XPath

正文不存 HTML，只存段落纯文本；同一个文件导入两次，切出来的段落是一样的。
所以一条划线记 `{p, s, e}` 就够复原，不需要 DOM 路径那一套 —— 后者一改渲染就全废。
另外把划中的原文一起存着（`t`），摘录列表因此不用把整本书从 IndexedDB 读回来就能显示。

笔记有 1000 字上限。理由不是屏幕，是同步：整个 `S` 要塞进一个 256 KB 的请求体
（`server.js` 的 `MAX_BODY`），不设上限的话，某一天备份会毫无征兆地开始失败。

### 演示那句英文自带词条，不去拉词典

`public/js/demo.js` 里硬编码了六条 ECDICT 词条，下载页和首页空态共用。
看着像是「本该去查真词典」的偷懒，其实反过来：真词典按首两字母分片，
这六个词落在六片上，加起来 1.6 MB。为了演示「点一下就出」先下 1.6 MB，
正好把要证明的事情证伪了。

（真实阅读里之所以点一下就出，是因为进一节之前 `ensureSectionDict` 已经把
这一节要用的分片准备好了。演示自带数据是同一个道理，不是特例。）

代价是同一份数据存了两处。`test/demo.js` 第一条就是拿 `public/dict/` 逐字比对，
对不上直接判失败 —— 「广告上写一套、装完是另一套」是这个功能唯一真正的风险。

### 词典收了 35 万词，不是 43 万

产品构想里估的是「43 万词条 / 51.3 MB / gzip 11.9 MB」。实际做下来是
**35.5 万词 / 28.8 MB / 647 个分片**——少掉的那些全是带空格的词组，
而正文分词用的是 `[A-Za-z]+(['-][A-Za-z]+)*`，词组永远不会被点到，收进来纯属浪费体积。

收词门槛是「有考纲标签 / 有常用度 / 有词频 / 有词形变化」，再加一条**拼接词补收**：
`cannot` 在 ECDICT 里有音标有释义（`aux. 无法, 不能`），却既没标签也没词频，
三条门槛全不占，就这么掉出去了，点它只能靠前端拆成 `can + not` ——
而 ECDICT 的 `can` 头一条义项是「装罐」，拼出来的解释很难看。
所以第二遍把「能拆成两个**简单**词」的词条补回来（3.5 万条，+2MB），
并在词条上打一个 `e:1`，前端判难易时直接认这个标记，不必再多拉一个分片。

两条试过但否掉的口子：
- 只要求「两半都在词典里」→ 救回 37.8 万条，体积 26.6MB 涨到 46.7MB。
  英文三字母词太多，几乎任何长词都能拆开。必须要求两半都是**简单词**。
- 「有音标就收」→ 多出 14.7 万条 `Laugiidae`、`thioureido` 这种生僻术语，
  体积涨四成、收益是零。

想全收：`--full`（129 万词 / 78 MB）。

### ⚠️ 分节不能用英文词数来度量（曾经整本书只剩一页）

这是本地版跑起来之后用户报的第一个 bug：一本几百页的书导进去**只剩第一页**。

根因在 `makeSections`：它拿 `countWords()`（只数 `[A-Za-z]+`）判断章节长短，
`total < 25` 就当成版权页丢掉。中文——以及任何非拉丁文字——的章节一律算 0 词，
于是**整本书 72 章全被丢光**，只有第一章因为混了几十个英文字符（推广文字里的 QQ 号）
活了下来。而且全程不报错，导入流程一路绿灯。

修法：分节和「短到可以丢」一律用 `textWeight()`（英文词 + 汉字 × 0.6）度量，
`countWords()` 只留给「估阅读时间」「算生词」这些真和英文有关的地方。
实测那本中文书从 1 节变成 74 节。

顺带补一个诚实的提示：英文占比低于 15% 时，预览页直说「这份文档里几乎没有英文，
查词帮不上忙」，而不是让人导进来才发现点哪个词都没反应。

### ⚠️ 「正文从哪开始」是书里写好的，不该猜

导一本书进来，第一屏是出版说明 —— 这是实测里最伤的一个体验问题。
根因是只读了 spine：**spine 是「文件在书里的排列顺序」，不是「正文从哪开始」**，
它头几项本来就是封面、扉页、版权页、致谢、目录。从第 0 节打开，就是让人读版权页。

而这件事出版社在文件里已经明确写好了，三处，按可信度排：

| 线索 | 出处 | 说的是什么 |
|---|---|---|
| `landmarks` 里的 `bodymatter` | EPUB3 的 nav 文档 | 字面意思就是「正文从这里开始」 |
| `<guide><reference type="text">` | EPUB2 的 OPF | 同上，老书的标准写法 |
| 文档自己的 `epub:type` | 每篇 XHTML | `copyright-page`、`toc`、`frontmatter`… |
| 标题匹配 | —— | 上面三样都没有时才用 |

章名也一并换了来源：优先用**目录里出版社写的标题**（nav 的 `epub:type="toc"`，
或 EPUB2 的 `toc.ncx`），而不是猜文里第一个 `<h1>`。

**PDF 只吃一种情况：书自己带了书签目录**（`getOutline()`）。有就照读，
把书签解析成页码、段落按页码归章；**没有就一节都不跳**，走原来的字号判定。
这个不对称是刻意的 —— EPUB 敢靠标题猜，是因为下面还垫着 landmarks / guide
两层标准字段；PDF 什么都没有，猜错就是把正文第一章跳掉。

#### 两道闸，和几条试过但否掉的口子

启发式那条路上卡了两道闸：

- **只匹配整个标题**。「Acknowledgments」是前置内容，「The Acknowledgment」
  是小说的一章，包含匹配会把后者一起误杀。
- **只在正文尚未开始之前猜**。一旦进了正文，后面再出现叫「Notes」的东西
  也可能是正文的一章。

否掉的：

- **spine 前 N 项一律当前置内容** → 有的书根本没有前置内容，正文第一章会被跳掉。
- **PDF 按字号 / 章节编号反推目录** → 无底洞，而且每多支持一种排版，
  覆盖的书只多一撮。没书签就不做。
- **PDF 书签指到页面中部时在页中切** → 一页两章的排法（散文集、诗集）确实存在，
  但要切准得把书签的 y 坐标和抽出来的行对齐，这两套坐标系在旋转页、裁剪框、
  多 MediaBox 的文件里对不上。整页归给该页第一个书签。
- **展开嵌套书签** → 「第三章 > 3.1 > 3.1.2」展开之后节比段还多，
  对「今晚读一节」这个单位是负作用。只取顶层。

#### 前置内容只是不作为起点，绝不删

这条是硬的。上一节那个「整本中文书只剩 1 节」就是自作主张删内容的代价，
而**悄悄跳过和悄悄丢弃，用户是分不出来的**。所以：导入预览明说跳过了几节、
都是些什么、从第几节开始；目录里折叠一行，随时能展开翻回去。
判定要是把整本书都算成了前置内容，一律推翻重来按正文处理 ——
宁可从版权页开始，也不能打开是一本空书。

按章选读也是顺这套数据出来的：`makeSections` 给每一节带上 `ci`（章序号）
和 `kind`，书架和阅读页各有一个「目录」入口。只有一章的文档（没书签的 PDF、
粘贴进来的一段英文）不露这个入口 —— 点开就一行，是纯噪音。

反向用例在 `test/toc.js` 里，**别删**：`div-para.epub` 和 `single.pdf`
盯的就是「不许乱跳」。为了跳版权页把正文第一章跳掉，比不跳严重得多。

### EPUB 的结构比想象中野

同一轮还查出两个会**静默少内容**的问题，都造了测试件盯着（`test/formats.js`）：

- **段落用 `<div>` 而不是 `<p>`** —— 原来的块级标签白名单只认 `p/h1-h6/li/...`，
  这种书一段正文都抽不出来。现在白名单包含 `div/section/article`，只取「叶子块」
  （自己是块级、里面不再套块级），并加了一条兜底：叶子块加起来不到正文六成就
  改按空行切原始文本。宁可段落分得糙，也不能悄悄少掉大半本。
- **OPF 写成 `<opf:itemref>`** —— `getElementsByTagName('itemref')` 按限定名匹配，
  一个都匹配不上，整本书报「没有找到正文章节」。现在一律按 `localName` 找。

### 「拒绝扫描件」真的只有一行代码

`getTextContent()` 返回 0 项就是扫描件。程序需要判断的只有这一件事，
剩下的「这本书抽得对不对」全部交给预览页让人眼看——零成本、零误判，
比一堆启发式规则准得多。这一刀砍下去，整个「难的部分」就没了。

### ⚠️ 不能无条件相信 ECDICT 的 `exchange`

ECDICT 说 `does` 的原形是 `doe`（母鹿）、`also` 的是 `conjurer`（魔术师）、
`some` 的是 `an`、`always` 的是 `alway`（古体）。**危害在于标签会跟着一起丢**：
`always` 本身标着 `zk gk`，归并成 `alway` 后没有任何标签，于是被判成
「四级以上生词」排进要背的列表。

修法写死在 `dict.js` 的 `isSimple()` 里：**判断难易度时取「原词形标签 ∪ 原形标签」
的并集，任一为简单词就算简单。** `test/dict.js` 专门盯着这四个词，改回去就会红。

顺带修掉的两个洞：`cannot` 在 ECDICT 里既没标签也没词频（收词时被滤掉了），
靠「拆成两个简单词」兜住；`huh` 的词频排名 3926 超出已掌握线，靠拟声词表兜住。
这两个词产品构想里都点了名。

### 缩写和所有格要按词干判难易

ECDICT 给 `wouldn't` / `isn't` / `one's` 的是「常用度 5、没有考纲标签、词频排名 0」——
标签、词频、拆词三条判据全都落空，于是满篇的 `wouldn't`、`isn't`、`I'm` 都被标成
超纲词，虚线密到没法看。而它们的词干 `would` / `is` / `one` 明明白白标着 `zk gk`。
现在含撇号的词一律回退到词干判断。

### 双栏检测必须在归行**之前**做

一开始按「行首 x 分两簇」判断，怎么都检不出来。原因是：双栏排版里左右两栏的行
y 坐标是一样的，按 y 归行的时候就已经被并成一行了，行首 x 永远只剩左栏那一个值。
（而这个「左右串成一句」正是双栏抽出来读不通的原因本身。）

现在改成在字符碎片的**横向覆盖直方图**上找版心中间那条没有字的竖直空档，
并且只统计版心——居中的页眉页码横跨整页，正好压在中缝上，算进来会把空档填平。
判据用「相对中位数的落差」而不是绝对阈值：单栏的覆盖是从左到右缓慢下滑的
（每段最后一行短），中段大约在中位数的 85%；双栏的中缝直接掉到 0。

### 节内词表收全部生词，不是只收「出现 ≥3 次」的

产品构想里同时写了两个数：漏斗末端是「121 核心词（出现 ≥3 次）」，
产品形态是「今晚：第 12 节 · 17 个新词」。**这两个是不同的东西**——
一开始按 ≥3 筛节内词表，结果每节中位数只有 2 个词（核心词总共一百多个，
摊到几十节上当然没剩几个）。

现在节内词表收**全部生词**，按书内频次降序排，`≥3` 只用来标「后面还会反复撞见」。
理由：目的是让**今晚这一节**读起来省力，不是攒一辈子的词汇量；只出现一次的词
今晚照样会撞见。而「时间不够就只做前半段」靠的正是那个频次降序。

实测下来每节中位数 10 个词（1–23），和构想里说的 17 个是一个量级。

### 一个没料到的副作用：扫一本书 ≈ 把词典下完了

导入一本 6 万词的书要查 4561 个词形，这些词形散落在 620 / 647 个分片里——
所以扫完一本书，词典已经缓存了 96%。「显式下载完整词典」那个按钮因此更像是
**补齐最后 4%**，而不是从零开始下。这不影响体验（本地和 Wi-Fi 下都很快），
但如果以后真的上线，不如老老实实在导入前就把整包下完，比装作按需加载更坦荡。

（导一份几千词的合同就不会有这个问题——那只会碰到几十个分片。）

## 实测数据（《被讨厌的勇气》英文版 EPUB，6.2 万词）

```
4,561 unique 词形
  → 4,508 在词典里查到
  →   831 生词（滤掉：简单词 / 缩写所有格 / 专有名词 / 拟声词）
  →   137 出现 >= 3 次
84 节，每节新词 中位数 10（最少 1，最多 23）
书内 Top: interpersonal(143) inferiority(91) superiority(40) self-acceptance(24) blush(23)
```

Top 5 正是阿德勒心理学的核心概念——这就是**频次不设上限**的理由：
一个词出现 143 次，学一次回本 143 次；设上限会砍掉最该学的那几个。

## 存储

| 东西 | 存在哪 | 丢了怎么办 |
|---|---|---|
| 文档正文、词汇索引 | IndexedDB | 重新导入一次，原文件还在你手机上 |
| 阅读进度、生词本、划线和笔记 | localStorage + 服务器同步码 | **不能丢**，所以才要上服务器 |
| 词典分片 | Cache API | 重新下 |

iOS Safari 在存储紧张时会清掉网页的 IndexedDB。加到主屏当 PWA 用 +
`navigator.storage.persist()` 能大幅降低概率，但不能保证——这正好又是
「进度必须上服务器」的理由。

## 还没做

- 章节目录（PDF 靠字号猜标题，EPUB 用 spine 顺序，都还没有可跳转的 TOC）
- 阅读位置只记到「第几节」，没有记到段落（划线倒是记到了字符，见 `hl.js`）
- 词典分两档（基础版 / 完整版）——见构想里的未决问题
- 中文等非拉丁文字只是**不再被丢掉**，并没有做查词（那要分词器，是另一个问题域）
- 旧版 `.doc`（只支持 `.docx`）、扫描件 OCR
- 上架（APK 目前是自签名、侧载安装）；iOS 那边什么都还没有

词典数据来自开源项目 [ECDICT](https://github.com/skywind3000/ECDICT)（MIT 协议）。
`collins` / `oxford` 这两个品牌标签已经在构建时丢掉了，界面上只显示中性的「常用度 ★」。
